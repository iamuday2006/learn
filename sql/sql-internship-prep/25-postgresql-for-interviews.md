# 25 — PostgreSQL for Interviews 🔥

**Priority: 🔥 MUST KNOW** — the "Why PostgreSQL?" follow-up is common.

---

## Concept — know the list, not internals

PostgreSQL is your primary DB. Interviewers will test whether you understand its **model** and **feature set**, not its code. Focus on:

### Architecture at a glance

- **Process model** — one process per connection (lighter than thread-per-conn in some DBs).
- **WAL** — Write-Ahead Log: durable; enables recovery, replication, streaming.
- **MVCC** — Multi-Version Concurrency Control: readers don't block writers (ch 21).
- **Shared buffers + OS cache** — double-buffering; you can check `shared_buffers` size.
- **VACUUM** — reclaim dead tuples (MVCC byproduct, not a DBA concern).

### Key features to mention confidently

| Feature | Interview note |
|---------|---------------|
| **SERIAL / IDENTITY** | `SERIAL` = sequence (defaut) / `GENERATED AS IDENTITY` (standard SQL, preferred) |
| **UUID** | `uuid_generate_v4()` or `gen_random_uuid()` (PG13+ native) — globally unique PKs for distributed systems |
| **JSONB** | Binary JSON: storage-efficient, indexable, supports `@>`, `?`, `->`, `->>`, `#>>`, GIN index |
| **ARRAY** | Native column arrays: `INT[]`, supports `ANY`, `unnest`, `array_agg` |
| **TIMESTAMPTZ** | Date+time with timezone awareness; UTC storage |
| **FUNCTIONS** | Hundreds of built-ins; great for analytics (window, date, string, aggregate) |
| **UPSERT** | `INSERT ... ON CONFLICT ... DO UPDATE/NOTHING` |
| **CTE (destructive)** | `WITH cte AS MATERIALIZED` to force materialization |
| **Extensions** | `pg_trgm`, `btree_gin`, `pg_stat_statements`, `TimescaleDB`, `PostGIS` |

## SQL syntax PostgreSQL loves

```sql
-- IDENTITY (standard)
CREATE TABLE users (
    id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);

-- JSONB
CREATE TABLE events (
    id SERIAL PRIMARY KEY,
    payload JSONB
);
SELECT payload->>'user_id' FROM events WHERE payload @> '{"action":"click"}';
CREATE INDEX idx_payload ON events USING GIN (payload);

-- FILTER clause (clean conditional aggregates)
SELECT COUNT(*) FILTER (WHERE status = 'done') AS done
FROM orders;

-- DISTINCT ON (PG gem)
SELECT DISTINCT ON (customer_id) *
FROM orders ORDER BY customer_id, order_date DESC;

-- generate_series
SELECT * FROM generate_series(1, 10);

-- Array functions
SELECT unnest(ARRAY[1,2,3]);
```

## Interview Question (Level 3)

**Q:** Why do you prefer PostgreSQL?

**30-second answer:** "Full ACID support, advanced SQL (window functions, CTEs, JSONB, FILTER), strong extension ecosystem (TimescaleDB for time series, pg_trgm for fuzzy search), reliable concurrency via MVCC, and transactional DDL."

**Follow-up:** "Is it always the best choice?"
**Answer:** No — for simple high-traffic OLTP with minimal joins, MySQL/MariaDB is fast and battle-tested. PostgreSQL's strength is when you need complex analytics, data integrity, or schema flexibility (JSONB + arrays).

## Tricky Question (Level 5)

**Q:** What is the difference between `SERIAL` and `IDENTITY`?

- `SERIAL` creates a sequence + sets the default; you can still **manually insert a value** into the `id` column (bypassing the sequence). Over time, the sequence can get out of sync.
- `IDENTITY` column is enforced: if you try to manually insert into it with `GENERATED ALWAYS`, it errors. Use `GENERATED BY DEFAULT` to allow manual inserts.

PostgreSQL recommends `IDENTITY` for new code.

## Interview Follow-Up Chain

**Q:** "What is JSONB best used for?"  
**A:** Semi-structured event payloads (`payload` column in `events`), user preferences, dynamic attributes. Best indexed with GIN; for repeated queries on specific keys, extract to real columns.

**Q:** "ARRAY column vs JSONB vs relation?"  
**A:** ARRAY is lightweight, fast for `ANY`/`unnest`. JSONB is flexible for nested, schemaless data. A relation is best when you have queries across attributes. ARRAY columns are not generally queryable via joins as easily.

**Q:** "Why did you choose TIMESTAMPTZ?"  
**A:** Because `TIMESTAMP` (without tz) ignores timezone ambiguity; `TIMESTAMPTZ` stores UTC and displays in session timezone — correct for distributed systems.

## Real-world scenario

You need to log user actions with flexible, schemaless data + be able to query "all events where action='purchase'":

```sql
CREATE TABLE user_events (
    event_id  SERIAL PRIMARY KEY,
    user_id   INT NOT NULL,
    action    VARCHAR(50),
    payload   JSONB,
    event_ts  TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_user_events_action ON user_events (action);
CREATE INDEX idx_user_events_payload ON user_events USING GIN (payload);
```

Now query:
```sql
SELECT * FROM user_events WHERE payload @> '{"campaign":"holiday"}';
SELECT payload->>'browser' FROM user_events WHERE action = 'view';
```
